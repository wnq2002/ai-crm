# AI CRM V1.3｜市场部线索优先管理系统 PRD

> 文档日期：2026-10-10  
> 文档定位：可交付生产系统的产品需求与实施基线，替换 V1.2。  
> 核心变更：**先收线索，再自动关联企业；市场部统一初筛，不设初筛负责人；快捷跟进；确认有效后交接业务部门；客户档案独立沉淀；统计支持领导汇报。**  
> 文档中的真实数据接入属于未来扩展，**不能视为本期已接入官网或邮箱**。

## 1. 业务背景、目标与范围

市场部接收来自演讲/展会、电话、微信、官网表单、邮箱、转介绍等渠道的咨询。当前渠道来源不固定，首先支持手动创建与 Excel 导入；未来再接官网、邮箱等自动入口。市场部负责先联系客户、核实需求是否真实、判断由哪个部门承接，之后记录部门进展反馈。公司需要集中资料、提高日常记录效率、为管理汇报提供可追溯数据。

本期目标：
1. **线索优先**：无须预先查询/创建企业；任何渠道的新咨询先保存为一条线索（可无企业名称），保存后系统检查可关联企业。
2. **企业去重沉淀**：一个企业可以有多条不同需求的线索，统计时区分「线索数量」与「去重企业数量」。
3. **市场部轻量操作**：线索列表一键「电话 +1」「微信 +1」，可选补充重要沟通内容；每次事件可追溯到操作人及时间。
4. **市场部初筛与交接**：确认有效后选择 GDC / Token 供应链 / 润效营及相应对接人；部门不必登录系统，市场部补充反馈。
5. **信息与汇报**：可按时间、来源（包括具体活动）、需求、部门及状态检索、统计、导出。

明确不做：不设置初筛负责人/分配给市场部成员的流程；不做复杂销售商机、报价、合同、收款；不强制部门对接人登录；不做主动爬取企业或 AI 自动外呼、群发；不假装官网/邮件已经连通；不做多租户 SaaS。AI 摘要和交接草稿是可选非阻塞增强，不能替代真实记录。

## 2. 用户、菜单与权限

### 2.1 角色
- `market` 市场部：创建/导入线索、处理企业关联、快捷跟进、判定需求、交接部门、补录反馈、查看本部门数据、受控导出。
- `admin` 管理员：拥有上述权限，同时管理账号、渠道/具体来源、部门和默认对接人、企业合并、撤销误操作、系统配置及审计。
- 仅记录创建人、跟进操作人、判定/交接操作人，不设置“初筛负责人”业务字段。
- 所有敏感操作在服务端鉴权，不能仅隐藏前端按钮。

### 2.2 主导航（5 项）
1. **工作台**：待处理、近期新增、近期联系、待交接、长期无反馈、数据摘要与快捷新建。
2. **线索管理**：全部线索、详情、新建、Excel 导入、查询筛选、快捷跟进、判断、交接和反馈；**默认业务入口**。
3. **客户管理**：企业列表、企业详情、联系人、关联全部线索；以自动关联/后台沉淀为主，不强制日常手工操作。
4. **数据分析**：线索、企业、渠道与活动、市场沟通工作量、有效性、部门交接和反馈；筛选及导出。
5. **系统设置**：市场部账号、来源类型/具体活动、部门和对接人、必要字典、可选 AI 配置。

不增加独立商机管理、销售任务中心、跟进中心。

## 3. 业务对象及核心关系

- **线索 Lead**：一次独立的客户咨询/需求，可能来自活动或官网。必须独立保存原始来源和原始内容。一个人/同一企业可以产生多条真实线索。
- **客户 Company**：一家企业的标准档案，可选关联到多个线索；企业归属不确定时线索的 `company_id` 可为 `NULL`。
- **联系人 Contact**：具体人员，属于某企业或暂不确定所属企业；线索保存原始的联系人快照并可选关联联系人对象。
- **来源 Source**：区分 `source_category`（线下活动、官网、邮箱、电话、微信、转介绍、其他、未知）与 `source_detail`（具体演讲/展会名称、官网表单名称等）。
- **录入方式 Intake**：手动、批量导入、API；与来源渠道严格区分。市场人员手动录入官网来的线索，来源仍应为“官网”，录入方式为“手动”。
- **跟进 Activity**：市场成员点击快捷记录或补充备注产生的不可无痕修改事件。
- **交接 Handoff**：有效线索对应的业务部门、对接人及历史流转。
- **进展反馈 Outcome**：市场部收到部门反馈后补录；不等于直接接入业务系统验证。

案例：线下演讲中获取「XX 科技有限公司／刘XX／手机号／OPC Team 使用需求」，官网表单收到「提交时间、姓名、电话、邮箱、公司名称、AI Agent / 智能体、研发智能体」。它们均**先创建线索**。若未来发现属于同一家企业，可关联同一个 `Company`，但线索仍各自独立，来源和需求不丢失。

### 3.1 “去重”必须区分三个层次
1. **同一次技术提交重复**：相同渠道事件 ID、导入任务唯一键或同一幂等键 → 阻止重复写入；属于系统幂等，不应算新线索。
2. **同一次咨询可能重复录入**：例如同一联系人、同一需求、相近时间；仅提示疑似重复，员工可查看并选择保留新线索或关联既有记录；不擅自删除。
3. **同企业多次不同需求咨询**：允许保留多条线索并关联一个客户；不能以公司相同为由拦截新线索。

手机号/邮箱是辅助匹配线索/联系人证据，**不能单独证明两家企业相同**；企业名称做规范化候选匹配，人工确认跨企业合并。

## 4. 端到端业务流程

1. 市场部收到咨询 → **直接新建线索**或 Excel 导入；未来自动渠道走相同入库服务。
2. 保存原始信息和来源 → 系统执行技术幂等检查、企业/联系人匹配；无企业也可录入（条件见 5.2）。
3. 匹配结果：确定归属则建立关联；不确定时显示“可能关联企业”，员工可忽略暂不处理，**不阻止新建和后续跟进**。
4. 市场部与咨询人沟通 → 在列表或详情快捷点电话 +1、微信 +1；重要内容才补备注，自动保存操作时间、人和次数。
5. 需求真实性：待确认（默认）/ 有效 / 无效；无效须记录原因，待确认可继续跟进。
6. 有效线索才可交接 → 选择业务部门、默认对接人和可选交接摘要；记录交接日期、操作人，允许授权更正交接并保留历史。
7. 市场部后续根据部门反馈登记：暂无反馈 / 推进中 / 已成交 / 未成交。未收到反馈不能推断为未成交。
8. 工作台和分析报表以真实记录汇总；按操作事件时间、线索获取时间等分别说明统计口径。

## 5. 页面与交互规范

### 5.1 工作台
- 指标：指定期间新增线索、去重企业、待确认、有效、已交接、暂无反馈、电话总次数、微信记录量、已知成交数。
- 待处理区：待确认、有效未交接、交接长期未收到反馈；可点击筛选跳转线索列表。
- 最近动态：新建、跟进、判断、交接、反馈、企业关联，显示事件时间和操作人。
- 全部来源于服务器真实数据；无固定模拟数据。

### 5.2 线索新建/编辑
最小字段：

| 字段 | 要求 | 说明 |
|---|---|---|
| 获取时间 `occurred_at` | 必填，默认当前时间 | 真实咨询/相识时间，可补录 |
| 姓名 | 选填 | 可只知手机号或公司 |
| 手机号/邮箱/微信号 | 至少一种，或有可追溯的渠道外部事件 ID | 支持部分渠道无手机号；后续可补全 |
| 企业名称原文 | **选填** | 不要求先搜索/创建客户 |
| 需求类型 | 选填 | AI Agent、OPC Team 等可配置，不等于部门 |
| 需求描述 | 可选，但至少填联系人/联系方式/需求描述之一且有可追溯来源 | 活动首次相识可能只留下联系方式 |
| 来源类型 | 默认未知，可后补 | 线下活动/官网/邮箱等 |
| 来源详情 | 选填 | 具体演讲名称、表单名称、推荐人说明 |
| 备注 | 选填 | 补充说明 |

校验底线：不能保存完全无可识别内容的空线索；要求至少有**联系方式、可识别姓名+来源信息、需求描述+来源信息、或可信外部事件引用**之一；对于“只有姓名且无法区分对象”的记录提示信息不足。字段空缺以“待补全”展示，不伪造企业名、手机号或邮箱。前端与 API 校验规则一致。

- `source_category` 与 `intake_method` 分开记录；提供“新增来源详情”选项（受控输入，避免来源字典爆炸）。
- 保存后自动检查已有企业，**先成功保存线索，再展示可能关联客户的非阻塞提示**；不需要先选企业。
- 编辑原始字段时保留修改历史；对于 API 来源额外持久化原始快照，不直接覆盖原始事件。

### 5.3 线索列表（高频入口）
- 默认按获取时间倒序，列：获取时间、来源类型/详情、企业名称（或“未填写”）、联系人、联系方式脱敏摘要、需求类型、需求摘要、需求判断、当前部门/对接人、后续进展、最近跟进、操作。
- 搜索企业、联系人、手机号/邮箱、需求关键词；筛选日期、来源类型、具体活动、需求类型、需求真实性、交接部门、进展；服务端分页/排序。
- 行快捷操作：**「电话 +1」「微信 +1」「备注」「查看」「交接」**。电话 +2/+3 放在展开菜单或详情中，避免列表太拥挤。点击 +1 即保存事件，无须再填表；微信 +1 同理。
- 点击后显示成功反馈和可短时撤销入口（撤销应调用有审计的撤销接口）；加载时禁用防止重复；服务端利用 idempotency key 防重复写入。
- 最近一次跟进、电话累计数和微信记录数由有效事件计算，不信任前端累计值。
- 允许多列适配与长文本省略，能快速打开详情；空/加载/失败/权限不足状态清楚。

### 5.4 线索详情
- 顶部：原始咨询信息、来源和时间、关联企业/联系人（如果已确认），可编辑；提示疑似匹配企业（可手工关联/解除，需审计）。
- 市场沟通：电话 +1/+2/+3、微信 +1，备注独立输入（可选择关联某条沟通事件），允许补录实际发生时间。默认记录时间为服务端当前时间，避免信任客户端时钟。
- 时间线：创建、电话、微信、备注、需求判断、企业关联、交接、反馈、撤销等；展示操作人、发生时间和记录时间区别。
- 初筛结论：待确认、有效、无效；无效必填原因，保存变更审计；电话次数不得自动改为有效。
- 部门交接：仅有效可操作，选部门→默认对接人可改选→可填摘要→确认；展示历史交接与当前部门。
- 反馈：暂无反馈（默认）、部门推进中、已成交、未成交；最终结果需反馈依据简述及反馈时间；所有变化留痕。

### 5.5 客户管理（恢复但保持轻量）
- 企业列表：企业名称、行业（选填）、联系电话/官网（选填）、关联线索数、最近咨询时间。
- 企业详情：标准名称及别名、联系人（多名）、全部关联线索及来源、历史需求与沟通汇总；点击线索返回其详情。
- 从线索产生客户：对于可信且可确认企业名，系统可自动关联**唯一完全匹配且已存在的企业**；对于新名称建议在后台生成待确认企业候选/在人工关联时创建客户，不能因模糊匹配直接合并。
- 同一企业多线索保留独立来源、需求和时间。企业合并限管理员，需预览影响、保留原始线索快照与审计。
- 不要求市场人员新建线索前打开客户管理，也不强制企业档案字段齐全。

### 5.6 Excel / CSV 导入
- 提供模板：获取时间、姓名、手机号、邮箱、微信号、企业名称、需求类型、需求描述、来源类型、来源详情、备注。
- 支持 `.xlsx`/`.csv`；字段映射、预览、格式校验、疑似重复提示、部分成功、失败行原因及下载错误明细。
- 导入不需要先生成企业；成功后走统一线索业务规则，后台匹配客户。
- 支持文件大小/行数上限可配置；批次与行号持久化，重试不得重复导入已提交行。

### 5.7 数据分析与汇报
- 默认本月，提供自定义时间范围（统一 Asia/Shanghai 展示，数据库 UTC 存储），各指标标明是按咨询发生时间、系统创建时间、交接时间、跟进时间或反馈时间统计。
- 指标：咨询线索数（不同咨询记录）、去重企业数（已关联的不同公司；未关联线索单列）、市场实际记录电话拨打次数、微信跟进事件数、已判断有效/无效/待确认、有效率、部门当前交接分布、交接次数（含改派单独展示）、暂无反馈/推进中/赢单/输单数量。
- 线索来源分析：按来源类型和来源详情（活动名、官网表单等）对比数量、有效数、交接数；线索归属原始来源不因后续改派而变化。
- 活动工作量按操作者统计，不设置初筛负责人；明确人工记录的电话次数不等同运营商核验通话次数。
- 有效率 = 有效 /（有效+无效），待确认独立展示；当分母为 0 显示 `—`，不要默认为 0%。
- 导出当前筛选的数据和指标，带数据口径说明；手机号/邮箱导出权限受控且记录审计；处理时区和 Excel 公式注入风险。

### 5.8 系统设置
- 部门与默认对接人：GDC—同事 A、Token 供应链—同事 B、润效营—同事 C；这些是**初始化可编辑配置**，不得写死。
- 来源类型、具体活动/来源详情、需求类型可维护、启停；不自动将 AI Agent 等需求类型绑定到某一个业务部门。
- 用户管理、角色权限、审计查看；可选 AI Key 仅后端保存，不对前端公开。

## 6. 核心状态及约束

- `qualification_status`: `pending` 待确认（默认）/ `valid` 有效 / `invalid` 无效。
- `handoff_status`: `not_handed_off`（默认）/ `handed_off`。
- `outcome_status`: `unknown` 暂无反馈（默认）/ `in_progress` 业务推进中 / `won` 已成交 / `lost` 未成交。
- 新线索无需部门/客户；只有有效线索可交接；未交接不得填写正式部门结果；需要撤销有效或改派时必须审计并保持字段一致性。
- 交接后市场部仍能看到、更新接到的业务进展；部门对接人是记录对象，不要求部门成员登录。
- `company_id` 可以为空；企业归属变化不能覆盖 `company_name_raw` 和来源快照。
- 删除使用归档/带审计撤销，不允许无痕硬删除业务历史。

## 7. 数据库（PostgreSQL）设计

建议最小表集合：

| 表 | 关键字段及职责 |
|---|---|
| `users` | id、username、password_hash、role、active、created_at 等 |
| `companies` | id、canonical_name、normalized_name、aliases、industry、created_at、merged_into_id nullable |
| `contacts` | id、company_id nullable、name、phone、email、wechat_id、created_at |
| `lead_source_categories` | id、code、name、active |
| `lead_source_details` | id、category_id、name、active |
| `lead_need_types` | id、name、active |
| `leads` | id、company_id nullable、contact_id nullable、company_name_raw、contact_name_raw、phone_raw、email_raw、wechat_raw、need_type_id、inquiry_text、occurred_at、source_category_id、source_detail_id nullable、source_detail_text、intake_method、external_source_event_id nullable、source_payload_json nullable、qualification_status、handoff_status、outcome_status、department_id nullable、department_contact_id nullable、created_by、created_at、updated_at、archived_at、version |
| `lead_activities` | id、lead_id、kind(phone/wechat/note)、phone_count nullable、content nullable、happened_at、created_at、created_by、revoked_at nullable、revoked_by nullable、revoke_reason、idempotency_key unique scoped to user/event |
| `departments` / `department_contacts` | 部门、部门对接人、默认关系及启停 |
| `lead_handoffs` | id、lead_id、from/to department、to_contact、note、happened_at、created_by、reason |
| `lead_outcome_events` | id、lead_id、from/to outcome、note、feedback_at、created_by、created_at |
| `lead_events` | 其他属性/判断/客户关联变更的审计事件，含前后值与操作者 |
| `import_jobs` / `import_rows` | 导入批次、文件校验、行级状态、幂等标识、错误报告 |
| `audit_logs` | 访问/导出/管理员修改等操作日志 |

约束：企业/联系人的外键可空；来源/需求字典停用不能破坏历史；`lead_activities.phone_count` 对电话只允许 1/2/3，微信或备注不得写入电话次数；唯一外部事件 ID 以渠道为范围；并发写需要版本号/事务约束；索引覆盖来源、发生时间、企业、状态、电话/邮箱规范化搜索；PII 字段按授权读取及日志脱敏。不要把一次公司匹配结果当作必然正确的客户事实。

## 8. API 设计（基线）

- 身份：`POST /api/auth/login`、`logout`、`change-password`、`GET /api/auth/me`。
- 线索：`GET/POST /api/leads`、`GET/PATCH /api/leads/{id}`、`GET /api/leads/{id}/timeline`、`POST /api/leads/{id}/archive`。
- 企业匹配：`GET /api/leads/{id}/company-candidates`、`POST /api/leads/{id}/link-company`、`DELETE /api/leads/{id}/company-link`（审计）、`GET/POST /api/companies`、`GET/PATCH /api/companies/{id}`、`GET /api/companies/{id}/leads`、管理员合并接口。
- 跟进：`POST /api/leads/{id}/activities`、`GET /api/leads/{id}/activities`、授权审计撤销接口；快捷动作也调用标准跟进 API，使用幂等键。
- 判断/交接/反馈：`POST /api/leads/{id}/qualification`、`POST /api/leads/{id}/handoff`、`POST /api/leads/{id}/outcome`。
- 导入导出：`POST /api/imports/preview`、`POST /api/imports/commit`、`GET /api/imports/{id}`、`GET /api/leads/export`。
- 统计：`GET /api/dashboard/summary`、`GET /api/reports/overview`、`GET /api/reports/sources`、`GET /api/reports/activities`、`GET /api/reports/handoffs`、`GET /api/reports/export`。
- 配置：用户、部门、部门联系人、来源分类/详情、需求类型 CRUD（管理员操作）。
- 未来渠道接入：独立 adapter/ingestion service，统一调用创建线索业务层；不能绕过数据校验/幂等/审计。

响应需包含字段级错误信息、稳定错误码、分页和排序；错误应能被前端展示。写接口事务化，外部重试不会重复创建或计数。

## 9. 确定技术栈与部署要求

| 层 | 选型 |
|---|---|
| Web 前端 | Vue 3 + TypeScript + Vite + Element Plus + Vue Router + Pinia |
| 后端 API | Python 3.12 + FastAPI + Pydantic v2 |
| ORM/迁移 | SQLAlchemy 2.x + Alembic |
| 数据库 | PostgreSQL 16+ |
| 文件导入 | openpyxl 与 CSV 标准库，隔离上传临时目录 |
| 身份与安全 | 服务端会话 + HttpOnly/Secure/SameSite Cookie，CSRF 防护、登录限流，Argon2id 密码哈希 |
| 反向代理 | Nginx + HTTPS |
| 容器部署 | Docker Compose，数据库持久化卷，服务健康检查 |
| 自动化测试 | Pytest（API、数据库集成）、Vitest（前端）、Playwright（E2E） |
| AI | 非阻塞可选功能；仅从有权限的数据生成客户/交接摘要草稿，失败不影响主流程 |

- 正式部署必须有环境变量模板、初始管理员创建命令、迁移脚本、数据库备份和恢复步骤、最小安全配置；不能用生产固定密码，不能自动造真实业务假数据。
- 保证日志不记录明文手机号、邮箱、会话密钥；导出受权限控制及审计；Excel 导出转义危险公式前缀；限制上传格式、容量、行数；做备份恢复演练。
- 建议目录：`frontend/`、`backend/`、`infra/`、`docs/PRD.md`、`docs/API.md`、`docs/DEPLOY.md`、`AGENTS.md`、`.env.example`。

## 10. 真实场景验收（必须使用真实数据库）

1. **演讲线索**：市场部直接录入“XX 科技有限公司、刘XX、联系电话、OPC Team 需求、来源=线下活动、活动名”，无需先创建企业，保存后可跟进。
2. **官网表单样例**：手动导入/录入提交时间、姓名、电话、空邮箱、公司名称、需求类型=AI Agent/智能体、需求描述=研发智能体；不要求邮箱，来源=官网，录入方式=手动/导入。
3. **无企业信息**：只有联系方式及简要来源也能创建线索，页面显示“企业待补全”。
4. **同企业不同需求**：新增第二条咨询，系统提示候选企业但允许保留两条线索；人工确认可关联到同一企业，两个来源/需求独立。
5. **疑似重复提交**：相同外部事件 ID 或同导入批次行的重复提交不会重复入库；类似文本不能粗暴删除。
6. **快捷记录**：列表点电话 +1 后立即看到数值 +1，操作人及服务器保存时间可查；网络重试不重复 +1。
7. **微信与备注**：微信 +1 独立记录；可选备注与补录实际发生时间；无需强制填写沟通正文。
8. **有效性初筛**：无初筛负责人字段；有效可交接、待确认不能交接、无效须填原因。
9. **部门交接**：有效线索选择 GDC/同事 A；可更改为 Token 供应链/同事 B 并保留历史；润效营/同事 C 可配置。
10. **反馈统计**：市场部补录推进中、成交、未成交；没有回复的线索显示暂无反馈，不计入未成交。
11. **客户管理**：企业详情能看到多个联系人与来自不同渠道的全部线索；合并操作可审计，不能丢失原文。
12. **报表**：在相同筛选条件下可分别得到线索数、去重企业数、电话次数、微信事件数、各活动来源的有效量、交接量及结果，导出数据与列表一致。
13. **权限并发**：市场人员不可修改系统设置或合并企业；管理员可审计；多人编辑时不静默覆盖。
14. **生产交付**：空数据库环境一键按说明初始化并迁移，创建管理员和市场账号，完成完整流程，备份并恢复成功，无运行时 Mock 客户数据。

## 11. Codex 开发执行顺序与变更规则

1. **先检查现有项目与旧 PRD 的差异**：标记已开发模块；如有历史数据，做兼容迁移方案，不直接删旧表或清空数据。
2. 初始化仓库工程、数据库、认证/权限、日志和自动化测试基础。
3. 完成线索统一创建（手动/导入）、来源/需求类型字典、线索列表与详情、非阻塞企业匹配。
4. 完成企业客户档案、联系人及线索关联，确保同企业多线索关系成立。
5. 完成列表快捷电话/微信事件、独立备注、时间线、幂等与撤销审计。
6. 完成需求判断、部门/对接人交接、结果反馈及状态校验。
7. 完成工作台、数据统计、筛选、Excel/CSV 导出及口径一致性。
8. 完成 E2E、权限安全、部署、备份恢复，输出实际测试报告与已知限制。

实施要求：每个阶段完成后跑相关测试，禁止擅自增加 CRM 销售管道、智能获客模块等未定义功能；有歧义时记录决策并使用最保守、可扩展的实现。**先保证市场部业务信息化闭环，再做 AI 增强。**
