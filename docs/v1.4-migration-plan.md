# AI CRM V1.3 → V1.4 差异分析与迁移计划

> 基线切换：V1.4 产品需求变更说明（市场部线索管理平台）替换 V1.3 为唯一需求源。
> 日期：2026-10-10
> 关联：`docs/PRD.md`（V1.3）、`docs/architecture.md`、`docs/api-contract.md`、`docs/decisions.md`

## 0. 现状盘点（V1.3 实际落地状态）

**已建（经 V1.3 验收，94 后端测试全绿，覆盖率 89.40%）：**

- 后端：`users`/`user_sessions`/`audit_logs` + 15 张 V1.3 业务表（18 表），Alembic 5 个 revision，Argon2id + HttpOnly Cookie 会话 + CSRF 双提交，RBAC（admin/market），`/auth/*`、`/admin/users`、`/leads/*`、`/activities/*`、`/companies/*`、`/imports/*`、`/dashboard/*`、`/reports/*`、`/settings/*`、`/healthz`。
- 前端：登录/改密/工作台/线索/客户/报表/设置 视图，快捷跟进（电话/微信 +1）、时间线、导入、企业匹配等组件。
- 数据模型现状（关键）：`leads`（三维正交状态机 qualification/handoff/outcome）、`lead_activities`（kind=phone/wechat/note，电话 phone_count ∈ {1,2,3}）、`lead_handoffs`、`lead_outcome_events`、`lead_events`（通用业务审计 before/after JSON）、`companies`、`contacts`、`lead_source_categories`/`lead_source_details`、`lead_need_types`、`departments`/`department_contacts`、`import_jobs`/`import_rows`。
- `backend/app/ai/` 目录为空 → V1.3 AI 增强（摘要/交接草稿）未实现；V1.4 的「智能识别」需从零落地。

**数据库现状（真 PG16，Homebrew 本地）：**

| 表组 | 行数 |
|---|---|
| `users` | 1（admin 种子） |
| `departments` / `department_contacts` | 3 / 3 |
| `lead_source_categories` / `lead_source_details` | 8 / 0 |
| `lead_need_types` | 2 |
| `leads` / `lead_activities` / `companies` / `contacts` 等业务表 | 全部 0 |

**结论：兼容迁移 = 改结构 + 新增表 + 保留字典与账号，无业务数据搬迁压力。** 仍强制走 Alembic（AGENTS.md 红线 #4），不 drop/truncate 现有表。

## 1. V1.3 → V1.4 差异（核心）

| 维度 | V1.3 | V1.4 | 处理 |
|---|---|---|---|
| 联系事件 | `lead_activities`：电话「+1/+2/+3」累计 phone_count，微信/备注 | 每次电话/微信独立事件；电话含「联系结果（已接通/未接通/拒接）」；微信三态（发送申请/通过/沟通）；时间线统一 | **重点改造**：重构 `lead_activities`，废 phone_count，加 result + 微信子类型 |
| 事件时间线 | 已有 `GET /leads/{id}/timeline` | 统一活动时间线（创建/电话/微信申请/通过/沟通/有效性变化/移交/反馈变化），倒序 | 扩展 timeline 聚合 + 图标/类型区分 |
| 事件修正/补录 | 支持补录时间、撤销（软删除），无修改历史 | 已存事件可修正；必须保留修改前后值/操作人/时间/原因；未来时间禁止 | 新增 `lead_event_revisions` + 事件修正接口 |
| AI | 未实现（`ai/` 空） | 智能新增线索：粘贴原文 → 提取字段（置信度分级）→ 回填；AI 只提取不落库不建客户 | 新增 `lead_parse_records` + `/leads/parse` + AI Provider 适配层 + 前端粘贴识别区 |
| 线索状态 | qualification_status pending/valid/invalid | 待处理/有效/无效（语义一致） | 无需改表，前端文案对齐 |
| 部门反馈 | outcome_status unknown/in_progress/won/lost | 暂无反馈/推进中/已成交/未成交/**暂缓** | 新增 `deferred`（暂缓）枚举值 |
| 重复检查 | 企业匹配返回 candidates | 手机号/邮箱/企业名匹配提示 + 渠道重复推送阻止 + 允许关联已有企业 | 扩展创建前重复检查（新增端点或扩展 candidates） |
| 数据分析 | `/dashboard/summary` + `/reports/{overview,sources,activities,handoffs}` | 全局筛选区 + 核心指标区（11 指标）+ 趋势分析区 + 渠道与部门分析区 + 数据明细区；下钻 + Excel 导出；口径独立 | 重构报表：新增趋势时序、渠道×部门、11 指标、下钻、导出对齐筛选 |
| 系统设置 | 部门/对接人/来源分类/详情/需求类型/用户 | 部门管理、来源渠道管理（含具体活动）、需求类型管理、用户权限、**AI 配置（密钥不出后端）**、配置审计 | 新增 AI 配置 + 配置操作审计 + 失败错误提示 |
| 来源渠道 | 8 分类（含「线下活动」） | 官网、演讲、展会、邮箱等 | 来源可配置；seed 补充「演讲/展会」分类，不写死 |

## 2. 数据模型变更（字段/外键/约束由后端设计，满足 V1.4 业务语义）

### 2.1 表名映射（V1.4 需求表 → 现有表）

| V1.4 需求结构 | 现有表 | 处理 |
|---|---|---|
| `lead_parse_records`（AI 解析原文/字段/置信） | 无 | **新增** |
| `lead_events`（电话/微信联系事件） | `lead_activities` | **重构**（见 2.2），沿用表名 |
| `lead_event_revisions`（事件修改历史） | 无 | **新增** |
| `lead_transfers`（部门移交） | `lead_handoffs` | 复用（语义一致） |
| `lead_feedbacks`（部门反馈） | `lead_outcome_events` | 复用（语义一致） |
| `source_types`（来源配置） | `lead_source_categories` + `lead_source_details` | 复用（分类=渠道，详情=具体活动） |
| `requirement_types`（需求类型） | `lead_need_types` | 复用 |
| `departments`（部门配置） | `departments` + `department_contacts` | 复用 |

> **命名冲突裁决**：V1.3 的 `lead_events` 是通用审计事件（before/after JSON），与 V1.4 的「联系事件」语义不同。保留 `lead_events` 为审计事件不变，联系事件沿用 `lead_activities`（重构其字段语义）。避免重命名两张表带来的 FK/代码大面积改动（见 ADR-027）。

### 2.2 `lead_activities` 联系事件重构

- 删除 `phone_count` 列及其 `CheckConstraint(ck_lead_activities_phone_count)`（数据为空，安全）。
- 新增 `result`（可空字符串）：电话 → `connected`(已接通)/`unconnected`(未接通)/`rejected`(拒接)；微信/备注 → NULL。
- `kind` 枚举扩展：`phone` / `wechat_request`(发送好友申请) / `wechat_approved`(好友申请通过) / `wechat_chat`(微信沟通) / `note`(备注，保留 V1.3 能力)。
- 微信关系状态「待通过/已通过」**由事件实时派生**（最新一条微信事件决定），不落冗余列，避免不一致；`LeadDetail` 暴露派生字段 `wechat_relationship`。
- 保留 `content`、`happened_at`、`created_by`、`revoked_at/by/reason`（软删除）、`idempotency_key` 唯一约束。
- 电话累计次数 = 有效 `phone` 事件数实时聚合；接通次数 = `result=connected` 的事件数。

### 2.3 新增表

**`lead_parse_records`**（AI 解析记录）：`id`、`lead_id?`(创建后回填)、`raw_text`(原文，必须保留)、`parsed_json`(字段+置信度 JSONB)、`created_by`、`created_at`。

**`lead_event_revisions`**（事件修正历史）：`id`、`activity_id`(FK→lead_activities)、`before_json`、`after_json`、`reason`(必填)、`revised_by`(FK→users)、`created_at`。

**`app_settings`**（键值配置，AI 服务等）：`id`、`key`(唯一)、`value`(JSONB，密钥加密/脱敏存储)、`updated_by`、`updated_at`。用于管理员配置 AI Provider；**密钥读取不返回前端**（响应统一 mask）。

### 2.4 枚举变更

- `lead.outcome_status` 新增 `deferred`（暂缓）。String 列无 DB 约束，仅常量 + 前端字典 + seed 无需变动（历史空数据）。

## 3. 兼容迁移方案（Alembic，纯增量）

新增 revision（在 `b1e974ca9835` 之后）：

1. `lead_activities`：`op.drop_constraint(ck_lead_activities_phone_count)`、`op.drop_column(phone_count)`、`op.add_column(result)`。
2. 建 `lead_parse_records`、`lead_event_revisions`、`app_settings`（含索引/唯一约束/外键）。
3. `lead_source_categories` 补 seed：演讲、展会（幂等，走 `app/seed.py`，不入迁移）。
4. 不 drop/truncate 任何表；`leads`/`companies` 等不变。

> `users.role`、`lead_events` 等 V1.3 结构不动。迁移必须可 `upgrade`/`downgrade` 往返。

## 5. 关键设计决策（新增 ADR，见 decisions.md）

- **ADR-027**：联系事件沿用 `lead_activities`（重构语义），`lead_events` 保持审计职责；避免双表重命名。
- **ADR-028**：微信关系状态由事件实时派生（不入库），保证与事件历史强一致。
- **ADR-029**：AI 配置存 `app_settings`（服务端），密钥仅写入不读回（响应 mask）；AI 仅提取信息，不创建/修改客户数据；识别失败仍可手动创建线索。
- **ADR-030**：数据统计「线索数量」与「事件数量」严格分开（按 occurred_at / happened_at / 移交时间 / 反馈时间 分别口径），全部来自真实业务数据。
