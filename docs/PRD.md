## 1. 业务背景、目标与范围

市场部接收来自演讲/展会、电话、微信、官网表单、邮箱、转介绍等渠道的咨询。当前渠道来源不固定，首先支持手动创建与 Excel 导入；未来再接官网、邮箱等自动入口。市场部负责先联系客户、核实需求是否真实、判断由哪个部门承接，之后记录部门进展反馈。公司需要集中资料、提高日常记录效率、为管理汇报提供可追溯数据。

本期目标：
1. **线索优先**：无须预先查询/创建企业；任何渠道的新咨询先保存为一条线索（可无企业名称），保存后系统检查可关联企业。
2. **企业去重沉淀**：一个企业可以有多条不同需求的线索，统计时区分「线索数量」与「去重企业数量」。
3. **市场部轻量操作**：线索列表/详情一键记录电话（含接通结果）或微信（三态），可选补充重要沟通内容；每次事件可追溯到操作人及时间。
4. **市场部初筛与交接**：确认有效后选择 GDC / Token 供应链 / 润效营及相应对接人；部门不必登录系统，市场部补充反馈。
5. **信息与汇报**：可按时间、来源（包括具体活动）、需求、部门及状态检索、统计、导出。

明确不做：不设置初筛负责人/分配给市场部成员的流程；不做复杂销售商机、报价、合同、收款；不强制部门对接人登录；不做主动爬取企业或 AI 自动外呼、群发；不假装官网/邮件已经连通；不做多租户 SaaS。AI 摘要和交接草稿是可选非阻塞增强，不能替代真实记录。

## 2. 用户、菜单与权限

### 2.1 角色
- `market` 市场部：创建/导入线索、处理企业关联、快捷跟进、判定需求、交接部门、补录反馈、查看全部线索数据、受控导出。
- `admin` 管理员：拥有上述权限，同时管理账号、渠道/具体来源、部门和默认对接人、企业合并、撤销误操作、系统配置及审计。
- 仅记录创建人、跟进操作人、判定/交接操作人，不设置“初筛负责人”业务字段。
- 所有敏感操作在服务端鉴权，不能仅隐藏前端按钮。

### 2.2 主导航（5 项）
1. **工作台（待办驾驶舱）**：6 分类待办（已逾期/待首次跟进/今日待跟进/多次跟进无进展/长期未更新/交接待反馈）、最近动态、最近新增线索与近 30 天趋势。
2. **线索管理**：全部线索、详情、新建、Excel 导入、查询筛选、快捷跟进、判断、交接和反馈；**默认业务入口**。
3. **客户管理**：企业列表、企业详情、联系人、关联全部线索；以自动关联/后台沉淀为主，不强制日常手工操作。
4. **数据分析**：11 项核心指标、趋势、渠道 × 部门交叉、下钻明细；筛选及 Excel 导出。
5. **系统设置**：市场部账号、来源类型/具体活动、部门和对接人、必要字典、AI 配置 Tab（密钥不出后端）。

不增加独立商机管理、销售任务中心、跟进中心。

## 3. 业务对象及核心关系

- **线索 Lead**：一次独立的客户咨询/需求，可能来自活动或官网。必须独立保存原始来源和原始内容。一个人/同一企业可以产生多条真实线索。
- **客户 Company**：一家企业的标准档案，可选关联到多个线索；企业归属不确定时线索的 `company_id` 可为 `NULL`。
- **联系人 Contact**：具体人员，属于某企业或暂不确定所属企业；线索保存原始的联系人快照并可选关联联系人对象。
- **来源 Source**：区分 `source_category`（线下活动、官网、邮箱、电话、微信、转介绍、其他、未知）与 `source_detail`（具体演讲/展会名称、官网表单名称等）。
- **录入方式 Intake**：手动、批量导入、API；与来源渠道严格区分。市场人员手动录入官网来的线索，来源仍应为“官网”，录入方式为“手动”。
- **跟进 Activity**：市场成员点击快捷记录或补充备注产生的不可无痕修改事件。
- **交接 Handoff**：有效线索对应的业务部门、对接人及历史流转。
- **进展反馈 Outcome**：市场部收到部门反馈后补录；不等于直接接入业务系统验证。

案例：线下演讲中获取「XX 科技有限公司／刘XX／手机号／OPC Team 使用需求」，官网表单收到「提交时间、姓名、电话、邮箱、公司名称、AI Agent / 智能体、研发智能体」。它们均**先创建线索**。若未来发现属于同一家企业，可关联同一个 `Company`，但线索仍各自独立，来源和需求不丢失。

### 3.1 “去重”必须区分三个层次
1. **同一次技术提交重复**：相同渠道事件 ID、导入任务唯一键或同一幂等键 → 阻止重复写入；属于系统幂等，不应算新线索。
2. **同一次咨询可能重复录入**：例如同一联系人、同一需求、相近时间；仅提示疑似重复，员工可查看并选择保留新线索或关联既有记录；不擅自删除。
3. **同企业多次不同需求咨询**：允许保留多条线索并关联一个客户；不能以公司相同为由拦截新线索。

手机号/邮箱是辅助匹配线索/联系人证据，**不能单独证明两家企业相同**；企业名称做规范化候选匹配，人工确认跨企业合并。

## 4. 端到端业务流程

1. 市场部收到咨询 → **直接新建线索**或 Excel 导入；未来自动渠道走相同入库服务。
2. 保存原始信息和来源 → 系统执行技术幂等检查、企业/联系人匹配；无企业也可录入（条件见 5.2）。
3. 匹配结果：确定归属则建立关联；不确定时显示“可能关联企业”，员工可忽略暂不处理，**不阻止新建和后续跟进**。
4. 市场部与咨询人沟通 → 在列表或详情快捷记录电话（选择已接通/未接通/拒接）或微信（发送申请/通过/沟通）；重要内容才补备注，自动保存操作时间、人和次数。
5. 需求真实性：待确认（默认）/ 有效 / 无效；无效须记录原因，待确认可继续跟进。
6. 有效线索才可交接 → 选择业务部门、默认对接人和可选交接摘要；记录交接日期、操作人，允许授权更正交接并保留历史。
7. 市场部后续根据部门反馈登记：暂无反馈 / 推进中 / 已成交 / 未成交 / 暂缓。未收到反馈不能推断为未成交；暂缓表示确认延后、不等于输单。
8. 工作台和分析报表以真实记录汇总；按操作事件时间、线索获取时间等分别说明统计口径。

## 5. 页面与交互规范

### 5.1 工作台（待办驾驶舱）
- **今日工作概览**：6 分类待办计数卡——「已逾期 / 待首次跟进 / 今日待跟进 / 多次跟进无进展 / 长期未更新 / 交接待反馈」，点击跳转线索列表对应 `todo` 筛选；已逾期、今日待跟进在视觉层级上更突出。
- **优先处理列表**：按 已逾期 → 待首次跟进 → 今日待跟进 → 多次跟进无进展 → 长期未更新 → 交接待反馈 排序（每条线索只归入首个命中类别），每条显示企业/联系人、当前状态、跟进次数、最近跟进、下次跟进，并提供「记录跟进」「查看详情」。
- **最近动态**：时间线展示最近创建、跟进（电话/微信/备注）、判断、交接、反馈等事件与操作人。
- **最近新增线索**：展示最近 5 条，可进详情、查看全部；**近 30 天线索趋势**折线摘要。
- 全部来源于服务器真实数据；无固定模拟数据；无数据时显示明确空状态。

### 5.2 线索新建/编辑
最小字段：

| 字段 | 要求 | 说明 |
|---|---|---|
| 获取时间 `occurred_at` | 必填，默认当前时间 | 真实咨询/相识时间，可补录 |
| 姓名 | 选填 | 可只知手机号或公司 |
| 手机号/邮箱/微信号 | 至少一种，或有可追溯的渠道外部事件 ID | 支持部分渠道无手机号；后续可补全 |
| 企业名称原文 | **选填** | 不要求先搜索/创建客户 |
| 需求类型 | 选填 | AI Agent、OPC Team 等可配置，不等于部门 |
| 需求描述 | 可选，但至少填联系人/联系方式/需求描述之一且有可追溯来源 | 活动首次相识可能只留下联系方式 |
| 来源类型 | 默认未知，可后补 | 线下活动/官网/邮箱等 |
| 来源详情 | 选填 | 具体演讲名称、表单名称、推荐人说明 |
| 备注 | 选填 | 补充说明 |

校验底线：不能保存完全无可识别内容的空线索；要求至少有**联系方式、可识别姓名+来源信息、需求描述+来源信息、或可信外部事件引用**之一；对于“只有姓名且无法区分对象”的记录提示信息不足。字段空缺以“待补全”展示，不伪造企业名、手机号或邮箱。前端与 API 校验规则一致。

- `source_category` 与 `intake_method` 分开记录；提供“新增来源详情”选项（受控输入，避免来源字典爆炸）。
- 保存后自动检查已有企业，**先成功保存线索，再展示可能关联客户的非阻塞提示**；不需要先选企业。
- 编辑原始字段时保留修改历史；对于 API 来源额外持久化原始快照，不直接覆盖原始事件。
- **AI 粘贴识别（可选）**：可粘贴一段咨询文本，调用 `POST /api/leads/parse` 提取企业名/联系人/电话/邮箱/需求/来源等字段（带置信度），**仅提取回填表单，不落库、不建客户**；识别失败仍可手动填写创建。识别原文与解析结果在用户确认创建时随线索一并保存为解析记录（`lead_parse_records`）。

### 5.3 线索列表（高频入口）
- 默认按获取时间倒序，列：获取时间、来源、企业名称、联系人、联系方式脱敏摘要、需求摘要、跟进状态、最近跟进、操作（需求类型、当前部门/对接人等低频字段移至详情页）。
- 搜索企业、联系人、手机号/邮箱、需求关键词；筛选日期、来源、需求类型、交接部门、当前状态（判断×交接×进展合一）、待办类别；服务端分页/排序；支持从工作台跳转自动填充筛选。
- 行操作：主操作**「记录跟进」**（电话/微信/备注）、次操作**「查看」**，其余（标记有效/无效、交接、删除归档）收进「更多」菜单。
- 跟进状态列：待首次跟进 / 今日待跟进 / 已逾期 / 多次跟进无进展 / 长期未更新 / 正常，与工作台口径一致。
- 删除 = 归档（软删除），可在「查看已归档」中恢复；不允许无痕硬删除业务历史。
- 跟进次数、最近跟进时间由有效事件实时计算，不信任前端累计值；记录跟进后相关待办即时更新。
- 允许多列适配与长文本省略，能快速打开详情；空/加载/失败/权限不足状态清楚。

### 5.4 线索详情
- 顶部：原始咨询信息、来源和时间、关联企业/联系人（如果已确认），可编辑；提示疑似匹配企业（可手工关联/解除，需审计）。
- 市场沟通：电话（含接通结果：已接通/未接通/拒接）、微信三态（发送好友申请/好友申请通过/微信沟通），备注独立输入，允许补录实际发生时间。默认记录时间为服务端当前时间，避免信任客户端时钟。顶部汇总展示「电话累计」「微信记录」「微信关系（未添加/待通过/已通过）」。
- 微信「沟通」约束：仅当当前微信关系为「已通过」时才可选「微信沟通」；关系由最新一条有效微信事件实时派生。
- 记录跟进后：顶部提示条「已记录 电话/微信 + 撤销」，提供短时撤销（创建者本人或 admin 可撤销，填原因留痕）。
- 事件修正/补录：电话/微信事件可修正发生时间、接通结果、内容，`reason` 必填，写入 `lead_event_revisions` 留痕（前后值/操作人/时间/原因）；修正后的发生时间不得晚于当前时间。
- 时间线：创建、电话、微信、备注、需求判断、企业关联、交接、反馈、撤销等；展示操作人、发生时间和记录时间区别。
- 初筛结论：待确认、有效、无效；无效必填原因，保存变更审计；电话次数不得自动改为有效。
- 部门交接：仅有效可操作，选部门→默认对接人可改选→可填摘要→确认；展示历史交接与当前部门。
- 反馈：暂无反馈（默认）、部门推进中、已成交、未成交、暂缓；已成交/未成交需反馈依据简述及反馈时间；所有变化留痕。

### 5.5 客户管理（恢复但保持轻量）
- 企业列表：企业名称、行业（选填）、联系电话/官网（选填）、关联线索数、最近咨询时间。
- 企业详情：标准名称及别名、联系人（多名）、全部关联线索及来源、历史需求与沟通汇总；点击线索返回其详情。
- **线索 → 客户**：判「有效」时，若线索尚未关联客户（`company_id` 为空）且填有企业名称原文，则自动沉淀——企业名规范化后与唯一已有企业完全匹配则关联，否则（0 家/≥2 家/仅模糊匹配）**自动新建企业并关联**；同企业多条不同需求线索自动归到同一家企业。线索详情与客户页也支持手动「新建企业并关联」。
- 同一企业多线索保留独立来源、需求和时间。企业合并限管理员，需预览影响、保留原始线索快照与审计。
- 不要求市场人员新建线索前打开客户管理，也不强制企业档案字段齐全。

### 5.6 Excel / CSV 导入
- 提供模板：获取时间、姓名、手机号、邮箱、微信号、企业名称、需求类型、需求描述、来源类型、来源详情、备注。
- 支持 `.xlsx`/`.csv`；字段映射、预览、格式校验、疑似重复提示、部分成功、失败行原因及下载错误明细。
- 导入不需要先生成企业；成功后走统一线索业务规则，后台匹配客户。
- 支持文件大小/行数上限可配置；批次与行号持久化，重试不得重复导入已提交行。

### 5.7 数据分析与汇报
- 默认本月，提供全局筛选区（自定义时间范围，统一 Asia/Shanghai 展示，数据库 UTC 存储），各指标标明是按咨询发生时间、系统创建时间、交接时间、跟进时间或反馈时间统计。
- **核心指标区（11 指标）**：① 咨询线索数 ② 去重企业数 ③ 有效数 ④ 无效数 ⑤ 待确认数 ⑥ 有效率 ⑦ 已交接数 ⑧ 已成交（赢单）⑨ 未成交（输单）⑩ 推进中 ⑪ 暂无反馈；暂缓作为反馈态独立展示、不并入输单。
- **趋势分析区**：按日新增线索、有效、交接数的时序折线。
- **渠道与部门分析区**：来源分析（按来源类型对比数量/有效/交接，归属原始来源不因改派变化）；部门交接分布（含改派单独展示）；市场工作量按操作者统计（电话次数、微信事件数），不设置初筛负责人，人工记录的电话次数不等同运营商核验通话次数。
- **数据明细区 + 下钻**：各指标/图表可下钻到对齐相同筛选条件的线索列表；明细与列表一致。
- 有效率 = 有效 /（有效+无效），待确认独立展示；当分母为 0 显示 `—`，不要默认为 0%。
- Excel 导出对齐当前筛选（时间/口径），带数据口径说明；手机号/邮箱导出权限受控且记录审计；处理时区和 Excel 公式注入风险。

### 5.8 系统设置
- 部门与默认对接人：GDC—同事 A、Token 供应链—同事 B、润效营—同事 C；这些是**初始化可编辑配置**，不得写死。
- 部门/对接人/来源/需求类型支持**新增、编辑、删除、启停**；删除有引用保护（被历史引用则拦截，改用停用）；对接人支持**批量改派**（把名下存量线索转给同部门另一对接人，保留历史）。
- 来源类型初始化精简为「官网 / 其他」两项（未填来源默认归「其他」），后台可增改。
- 用户管理、角色权限、审计查看。
- **AI 配置 Tab**（粘贴识别用）：可配置 `provider`、`endpoint`、`model`、`timeout`（秒）；`api_key` 仅写入不回读（读回为脱敏占位 `***configured***`，仅返回 `api_key_configured` 布尔），支持清除；密钥仅后端保存、日志与审计脱敏，不对前端公开。

## 6. 核心状态及约束

- `qualification_status`: `pending` 待确认（默认）/ `valid` 有效 / `invalid` 无效。
- `handoff_status`: `not_handed_off`（默认）/ `handed_off`。
- `outcome_status`: `unknown` 暂无反馈（默认）/ `in_progress` 业务推进中 / `won` 已成交 / `lost` 未成交 / `deferred` 暂缓。
- 新线索无需部门/客户；只有有效线索可交接；未交接不得填写正式部门结果；需要撤销有效或改派时必须审计并保持字段一致性。
- 交接后市场部仍能看到、更新接到的业务进展；部门对接人是记录对象，不要求部门成员登录。
- `company_id` 可以为空；企业归属变化不能覆盖 `company_name_raw` 和来源快照。
- 删除使用归档/带审计撤销，不允许无痕硬删除业务历史。

### 6.1 跟进待办规则
- `next_follow_up_at`：下次计划跟进时间（记录跟进时可设/清空；备注不改变）。
- `follow_up_count` = 有效沟通事件数（电话 + 微信事件，排除备注与撤销），实时聚合、不落列。
- 待办分类（优先级从高到低，每条线索只归入首个命中类别）：① 已逾期（下次跟进早于今天）② 待首次跟进（跟进数为 0）③ 今日待跟进（下次跟进在今天）④ 多次跟进无进展（跟进 ≥3 次且未交接、无反馈）⑤ 长期未更新（已交接、无终态反馈、超过 7 天未跟进）⑥ 交接待反馈（已交接、暂无反馈、尚未达长期未更新阈值）。
- 分类仅用于提醒，不自动把线索判为无效。

## 13. 需求澄清决议（Clarifications）

> 本节是 V1.4 基线（市场部线索优先管理系统）的需求收敛结论，作为 api-contract / architecture / 验收的补充依据。
> V1.0 的 §19 决议（商机/任务/分配销售那套）随基线切换作废，不再适用。
> 维护：ProductAgent · 2026-10-13。文档对齐实现（V1.3 → V1.4），全部决议已由 team-lead 裁定定稿。

### 13.1 企业名称选填与校验底线（§5.2）

V1.4 允许不填企业名称直接建线索。§5.2 表格与「校验底线」段落口径重叠，统一为单一规则：

**可保存（满足其一即可）：**
1. 至少一种联系方式（手机号/邮箱/微信号）；或
2. 可识别姓名 + 来源信息（来源类型非「未知」，或已填来源详情）；或
3. 需求描述 + 来源信息；或
4. 可信外部事件引用（`external_source_event_id` 非空，仅 API/渠道来源）。

**硬拦截：** 姓名、联系方式、需求描述、外部事件引用全为空（完全无可识别内容）。
**提示信息不足并阻止保存：** 仅有姓名且无法与来源/联系方式/需求关联。

空缺字段以「待补全」展示；不伪造企业名/手机号/邮箱；前端与 API 校验规则一致。

### 13.2 去重三层次（§3.1）

| 层次 | 触发 | 处理 |
|---|---|---|
| 1 技术幂等 | 同渠道事件 ID / 同导入批次唯一键 / 同幂等键 | 阻止重复写入，返回首次结果 |
| 2 疑似重复录入 | 规范化手机号或邮箱命中既有线索；或（姓名+需求类型）相同且 `occurred_at` 相近 | 仅软提示候选，员工可保留新线索或关联既有记录，不自动删除 |
| 3 同企业多需求 | 企业名称相同 | 不拦截；多条线索可关联同一 `Company` |

手机号/邮箱/企业名是「匹配证据」而非「合并依据」；跨企业合并需管理员人工确认。

### 13.3 交接 / 反馈状态机约束（§6）

- `qualification_status`：`pending`（默认）→ `valid` / `invalid`；`invalid` 必填原因。
- 仅 `valid` 可交接：`handoff_status` `not_handed_off` → `handed_off`，必选部门 + 对接人。
- `outcome_status`：`unknown`（默认）→ `in_progress` / `won` / `lost` / `deferred`；仅 `handed_off` 后允许登记非 unknown 结果；`unknown` ≠ `lost`（未收到反馈不得推断未成交）；`deferred` 暂缓表示延后处理，不等于输单。
- 交接/反馈为事件流（`lead_handoffs` / `lead_outcome_events` 记录 from/to）；改派 = 新交接记录（from=旧部门，to=新部门），历史保留。
- qualification 变更：`handed_off` 之前 market 可变更（审计）；`handed_off` 之后任何 qualification 变更（含 valid→pending/invalid）**仅 admin 可执行且强制审计**。不引入「先撤销交接再撤销有效」两步；改派须审计并保持字段一致。

### 13.4 有效率分母为 0（§5.7）

有效率 = `valid / (valid + invalid)`；`pending`（待确认）独立展示、不计入分母。当 `valid + invalid = 0` 时，前端显示 `—`（em dash），不得显示 0% 或 NaN。

### 13.5 企业自动关联「唯一完全匹配」（§5.5）

自动关联仅当线索 `company_name_raw` 规范化后与**唯一一家**已有 `companies.normalized_name` 完全匹配时执行；命中 0 家 → 不关联（「企业待补全」）；命中 ≥2 家或仅模糊匹配 → 仅展示候选，人工选择。绝不因模糊匹配自动合并。

**判定有效自动沉淀（补充，§5.5）**：`qualify=valid` 且 `company_id` 为空、`company_name_raw` 有值时自动匹配——唯一完全匹配则关联；否则（0 家/≥2 家/仅模糊匹配）**自动以 `company_name_raw` 新建企业并关联**（`decision_service.qualify`，候选在此流程不阻塞、不提示）。此处是「新建」而非「合并」，与上述「绝不因模糊匹配自动合并」不冲突。

### 13.6 撤销 / 归档权限（§2.1/§5.3/§6）

- 跟进事件撤销（`lead_activities.revoked_at`）：**创建者本人或 admin**，填原因 + 审计；软撤销不物理删除，累计计数按有效事件聚合。事件修正（`PATCH /api/activities/{id}`）同样限创建者本人或 admin。
- 线索归档（`leads.archived_at`）：软删除（仅 admin），历史不可硬删。

### 13.7 PII 脱敏与导出受控（§5.3/§5.7）

- 列表联系方式脱敏展示（建议默认：手机号 `138****0000`、邮箱 `a***@x.com`）；详情完整可见（market/admin 有权限）。
- 导出（`GET /api/leads/export`、`GET /api/reports/export`）需权限 + 审计，记录导出人/时间/筛选范围；Excel/CSV 转义公式前缀。

### 13.8 AI 能力（§2.1/§5.8/§9）

V1.4 引入 AI 粘贴识别：`POST /api/leads/parse` 仅提取字段（不落库、不建客户），识别失败仍可手动创建；AI Provider 配置存于 `app_settings`（`/api/settings/ai`），密钥仅写不回读（读回脱敏占位），日志/审计脱敏。AI 仍为**非阻塞可选增强**，失败不影响主流程。

### 13.9 market 线索可见性（§2.1）

market 成员共享全部本部门线索，**无创建人隔离**（V1.4 维持此口径）。「不设初筛负责人/不分配市场成员」，线索归属是「市场部」整体；`created_by` / 操作人仅作审计记录，不据此做数据隔离。

### 13.10 联系事件重构（V1.4，§5.4/§6/§7）

- `lead_activities` 废除 `phone_count`；电话事件用 `result` 记三态：`connected` 已接通 / `unconnected` 未接通 / `rejected` 拒接（必填）。
- 微信事件三态：`wechat_request` 发送好友申请 / `wechat_approved` 好友申请通过 / `wechat_chat` 微信沟通；微信/备注不得写 `result`。
- 微信关系由最新一条有效微信事件实时派生：无微信事件 → `none` 未添加；最新为 `wechat_request` → `pending` 待通过；最新为 `wechat_approved`/`wechat_chat` → `approved` 已通过。微信「沟通」仅关系已通过时才可记录。
- 跟进计数 = 有效(未撤销)沟通事件数（排除 note），实时聚合、不落列；电话累计 = 有效 phone 事件数，微信记录 = 有效微信事件数。

### 13.11 事件修正 / 补录（V1.4，§5.4/§7）

- 电话/微信事件可修正发生时间、`result`、内容；`reason` 必填；写入 `lead_event_revisions`（前后值/操作人/时间/原因）；`created_at` 不可改。
- 修正权限同撤销：创建者本人或 admin；已撤销记录不可修正。
- 发生时间（新建或修正）不得晚于当前时间（未来时间禁止）；可补录过去时间。

### 13.12 AI 粘贴识别（V1.4，§5.2/§5.8）

- `POST /api/leads/parse` 输入原文，返回企业名/联系人/电话/邮箱/需求/来源等字段（带置信度）+ hints，**仅提取回填，不落库、不建客户**。
- 识别失败或置信度低不阻断，员工仍可手动创建；确认创建时原文与解析结果写入 `lead_parse_records`（`lead_id` 可空）。
- AI Provider 配置见 §13.8 / §5.8，密钥仅写不回读。

### 13.13 数据分析 11 指标与「暂缓」（V1.4，§5.7/§6）

- 核心指标区 11 项：线索数、去重企业数、有效、无效、待确认、有效率、已交接、已成交、未成交、推进中、暂无反馈。
- `outcome_status` 新增 `deferred` 暂缓：延后处理、不等于输单；不并入未成交统计，独立展示。
- 趋势（按日线索/有效/交接）、渠道分析、部门交接分布、工作量按操作者；下钻与 Excel 导出对齐当前筛选口径。
